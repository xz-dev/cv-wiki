### ⭐ 3月上旬 (03-01 ~ 03-07) - 新增

- [virtio-win/kvm-guest-drivers-windows] PR #1536 - 🔄 开放中 (2026-03-05) **[重大重构]**
  - **问题**: 原有系统内存单块大分配在长时运行的虚拟机中极易因内存碎片导致分配失败，限制了 8K/24K 等超高分辨率的支持；且单页 SGList 容易超出 QEMU 16384 entry 限制
  - **方案**: 
    1. 实现多块连续内存分配，使用 `1MB → 64KB → 32KB → 16KB → 4KB` 的梯级 fallback 策略
    2. 基于 Windows Segment Heap 原理（1MB 粒度分配）与 buddy system 特性，选择 1MB 作为首选块大小，避开 2MB large page 碎片悬崖
    3. 启用 `VIRTIO_RING_F_INDIRECT_DESC` 间接描述符支持，允许单次传输超出 virtqueue 容量限制的巨量内存段信息
  - **改动**: +304/-73 行，涉及 3 个文件
  - **影响**: 从根本上解决了 viogpu 大分辨率下的内存分配难题，理论支持至 24K 分辨率

### ⭐ 4月上旬 (04-01 ~ 04-09) - 新增

- [freebsd/freebsd-src] PR #2116 - 🔄 开放中 (2026-04-03) **[首次 FreeBSD 内核贡献]** (9,000 Stars)
  - **功能**: 实现 FreeBSD virtio_balloon 驱动中自 FreeBSD 9.0 以来缺失的两个 virtio 特性:
    1. `VIRTIO_BALLOON_F_STATS_VQ`: 通过 stats virtqueue 向 Hypervisor 报告客户机内存统计 (free, total, available, swap, faults, caches)
    2. `VIRTIO_BALLOON_F_DEFLATE_ON_OOM`: 内存压力时自动放气 balloon，将页面归还虚拟机内存子系统
  - **动机**: FreeBSD 客户机在 QEMU/KVM 下无法报告内存统计，Proxmox 等平台显示错误的客户机内存使用量；过度膨胀的 balloon 无法在内存压力下自动收缩
  - **改动**: +366/-25 行，2 个文件 (`virtio_balloon.c`, `virtio_balloon.h`)
  - **对齐**: 头文件定义与 OASIS virtio-v1.2 规范对齐 (feature bits, config struct, stat tags)
  - **关联**: [FreeBSD Bugzilla #292570](https://bugs.freebsd.org/bugzilla/show_bug.cgi?id=292570)
  - **意义**: VirtIO 专长从 Windows 驱动扩展至 FreeBSD 内核，展示跨 OS 虚拟化驱动能力

- [flatpak/flatpak] PR #6567 - ❌ 已关闭 (被维护者采纳为 #6569) (2026-04-08) (4,868 Stars) **[Linux 桌面基础设施]**
  - **问题**: Flatpak 1.16.4 中 Steam 无法启动，报 "requires Flatpak 1.12.0 or later" 错误
  - **诊断**: `flatpak_run_app()` 中 CVE-2026-34078 修复引入回归:
    1. runtime fd 选择分支检查了 `custom_app_fd` 而非 `custom_runtime_fd`，当 `custom_app_fd == APP_EMPTY(-3)` 且 `custom_runtime_fd == USR_ORIGINAL(-2)` 时命中 `g_assert_not_reached()` 导致进程中止
    2. 修复 (1) 后，`flatpak_run_add_extension_args()` 在 `original_app_target_path` 为 NULL 时仍被调用
  - **过程**: 发现问题 → 提交 Issue #6568 → 提交 PR #6566 (部分修复) → 提交 PR #6567 (完整修复) → 维护者 @smcv 在 PR #6569 中采纳并扩展修复，致谢 xz-dev
  - **体现**: 从用户报告追溯至 C 代码 CVE 修复回归的跨层级根因分析能力

- [gvalkov/python-evdev] PR #251 - 🔄 开放中 (2026-04-01) (376 Stars)
  - **功能**: 为 `InputDevice` 添加 `readonly` 参数，为 `list_devices()`/`is_device()` 添加 `writable` 参数
  - **动机**: 源自 numlockw 用户报告的触控板 LED 脉冲问题 ([Reddit](https://www.reddit.com/r/tuxedocomputers/comments/1rtj3c9/))
  - **内核分析**: 深入 `drivers/input/evdev.c` 源码，发现根因不是 `O_RDWR` vs `O_RDONLY`（内核 `evdev_open()` 不区分打开模式），而是重复的 open/close 循环触发了硬件驱动 `open()` 回调 (`hidinput_open()` → `hid_hw_open()` → USB/I2C 重初始化)
  - **改动**: +33/-7 行，2 个文件
  - **关联**: 与 [numlockw evdev-holder](../personal-projects/numlockw.md) 和 [hid-rgb-ctl](../personal-projects/hid-rgb-ctl.md) 同属 Linux 输入子系统领域

### 1. [virtio-win/kvm-guest-drivers-windows] PR #732 - 修复GPU驱动休眠后蓝屏

**基本信息**
- 🔗 **PR链接**: https://github.com/virtio-win/kvm-guest-drivers-windows/pull/732
- ⭐ **项目Stars**: 2,840
- 📅 **提交时间**: 2026-01-03
- ✅ **状态**: 已合并
- 🏷️ **标签**: `bug-fix` `bsod` `hibernate` `windows-driver` `stability`
- 📝 **改动**: +210 lines, 4 files

**问题描述**

VirtIO GPU驱动在Windows从休眠状态恢复后频繁出现蓝屏：

1. **错误表现**:
   - `DRIVER_IRQL_NOT_LESS_OR_EQUAL` (0x000000D1)
   - 错误位置: `viogpu.sys`
   - 发生时间: 系统从休眠恢复并重新初始化GPU时

2. **根本原因分析**:
   ```c
   // 在viogpudo.c文件中
   NTSTATUS VioGpuDod::HibernateRestore()
   {
       // 问题代码 - 无锁访问共享资源
       if (m_CurrentModes != NULL) {
           // 1. 显示模式信息已被清理但指针未置NULL
           // 2. 尝试访问无效内存区域
           // 3. 导致BSOD
           if (m_CurrentModes->Size > 0) {  // 访问无效内存
               InitCurrentMode();
           }
       }
       
       // 问题代码 - 资源映射错误
       if (!BuildPagingQueue()) {  // 如果在休眠前的资源没有正确释放
           return STATUS_UNSUCCESSFUL;
       }
   }
   ```

3. **复现步骤**:
   - Windows 10/11客户机在KVM/QEMU环境中
   - 使用VirtIO GPU驱动
   - 系统进入休眠
   - 唤醒系统 → BSOD

**解决方案**

全面重写休眠恢复流程，确保资源正确释放和重新初始化：

```c
// viogpudo.c - 修复后的代码

// 添加休眠状态跟踪
BOOLEAN m_IsHibernating = FALSE;
KSPIN_LOCK m_HibernateLock = NULL;

// 休眠准备
NTSTATUS VioGpuDod::PrepareForHibernate()
{
    KIRQL oldIrql;
    KeAcquireSpinLock(&m_HibernateLock, &oldIrql);
    m_IsHibernating = TRUE;
    
    // 安全释放资源
    if (m_CurrentModes != NULL) {
        // 记录当前状态以便恢复
        SaveDisplayState();
        
        // 安全释放GPU资源
        CleanupPagingQueue();
        ReleaseFrameBufferMappings();
    }
    
    KeReleaseSpinLock(&m_HibernateLock, oldIrql);
    return STATUS_SUCCESS;
}

// 休眠恢复
NTSTATUS VioGpuDod::HibernateRestore()
{
    NTSTATUS status = STATUS_SUCCESS;
    KIRQL oldIrql;
    
    DbgPrint(TRACE_LEVEL_INFORMATION, "%s: Restoring from hibernation\n", __FUNCTION__);
    
    KeAcquireSpinLock(&m_HibernateLock, &oldIrql);
    
    // 完全重新初始化GPU状态
    if (m_IsHibernating) {
        // 1. 重新初始化基本控制结构
        InitializeGpuAdapter();
        
        // 2. 重新建立命令队列
        status = BuildPagingQueue();
        if (!NT_SUCCESS(status)) {
            DbgPrint(TRACE_LEVEL_ERROR, "%s: Failed to rebuild paging queue, status: 0x%X\n", 
                     __FUNCTION__, status);
            goto Exit;
        }
        
        // 3. 恢复显示模式 (从保存的状态)
        status = RestoreDisplayState();
        if (!NT_SUCCESS(status)) {
            // 如果恢复失败，尝试设置安全默认值
            SetDefaultDisplayMode();
        }
        
        // 4. 重新扫描显示器
        RescanDisplayDevices();
        
        // 5. 发送通知给OS重新枚举显示设备
        NotifyDeviceChange();
        
        m_IsHibernating = FALSE;
    }
    
Exit:
    KeReleaseSpinLock(&m_HibernateLock, oldIrql);
    return status;
}

// 添加防止休眠期间访问GPU资源的保护
BOOLEAN VioGpuDod::IsSafeToAccessGpu()
{
    BOOLEAN isSafe = TRUE;
    KIRQL oldIrql;
    
    KeAcquireSpinLock(&m_HibernateLock, &oldIrql);
    if (m_IsHibernating) {
        isSafe = FALSE;
    }
    KeReleaseSpinLock(&m_HibernateLock, oldIrql);
    
    return isSafe;
}
```

**技术亮点**

1. **状态机设计**:
   - 使用明确的休眠状态跟踪
   - 所有GPU访问前检查状态
   - 防止休眠过程中的异步访问

2. **内存管理改进**:
   ```c
   // 避免悬垂指针和内存泄漏
   void VioGpuDod::ReleaseFrameBufferMappings()
   {
       KIRQL oldIrql;
       KeAcquireSpinLock(&m_FrameBufferLock, &oldIrql);
       
       for (UINT i = 0; i < MAX_VIEWS; i++) {
           if (m_FrameBuffers[i].Ptr != NULL) {
               // 正确取消映射
               MmUnmapIoSpace(m_FrameBuffers[i].Ptr, 
                             m_FrameBuffers[i].Size);
               
               // 重要：清除指针防止悬垂引用
               m_FrameBuffers[i].Ptr = NULL;
               m_FrameBuffers[i].Size = 0;
           }
       }
       
       KeReleaseSpinLock(&m_FrameBufferLock, oldIrql);
   }
   ```

3. **资源跟踪**:

   - 防止资源泄漏

4. **多级错误恢复**:
   ```c

   {

   }
   ```

### 2. [distrobox/distrobox] PR #985 - 增强PID命名空间隔离

**基本信息**
- 🔗 **PR链接**: https://github.com/distrobox/distrobox/pull/985
- ⭐ **项目Stars**: 12,500
- 📅 **提交时间**: 2026-01-18
- ✅ **状态**: 已合并
- 🏷️ **标签**: `feature` `pid-namespace` `podman` `systemd` `isolation`
- 📝 **改动**: +180 lines, 3 files

**问题描述**

distrobox在启用systemd的容器中存在PID命名空间隔离问题：

1. **现有限制**:
   - systemd在容器中需要作为PID 1运行
   - 默认共享宿主机的PID命名空间
   - 导致容器内进程可以看到宿主机进程

2. **用户需求**:
   - 增强容器隔离性
   - 支持在容器内运行需要完整PID命名空间的应用
   - 保持systemd功能的同时提高安全性

3. **技术冲突**:
   ```bash
   # 现有命令 - 功能不完整
   distrobox create --name test-box \
     --image fedora:37 \
     --init --additional-flags "--pid=host"
   
   # 问题：--init (systemd) 与 PID隔离存在冲突
   # systemd需要作为PID 1运行，但隔离的PID命名空间也需要自己的PID 1
   ```

**解决方案**

实现新的PID命名空间管理策略，兼容systemd需求：

```bash
#!/bin/bash
# distrobox-create - 增强版PID命名空间隔离

# 新增配置选项
DBX_PID_ISOLATION="default"  # 可选: default, isolated, host
DBX_INIT_APPROACH="auto"     # 可选: auto, systemd, none

# 主逻辑增强
generate_container_command() {
    # ... 现有代码 ...
    
    # 根据配置选择适当的PID命名空间策略
    case "${DBX_PID_ISOLATION}" in
        "isolated")
            if [ "${DBX_INIT_APPROACH}" = "systemd" ]; then
                # 特殊情况：需要systemd + PID隔离
                # 使用podman/docker的特殊参数组合
                container_command+=(--pid=private)
                container_command+=(--init-path=/usr/bin/distrobox-init-proxy)
            else
                # 标准PID隔离
                container_command+=(--pid=private)
            fi
            ;;
            
        "host")
            # 使用宿主机PID命名空间
            container_command+=(--pid=host)
            ;;
            
        "default"|*)
            # 默认行为取决于容器引擎和init方式
            if [ "${DBX_INIT_APPROACH}" = "systemd" ]; then
                # systemd默认需要使用宿主机PID
                container_command+=(--pid=host)
            fi
            ;;
    esac
    
    # ... 现有代码 ...
}
```

实现init代理来处理PID命名空间冲突：

```bash
#!/bin/bash
# /usr/bin/distrobox-init-proxy

# 此脚本作为容器内PID 1运行
# 目的：协调隔离的PID命名空间和systemd需求

# 检测我们是否在隔离的PID命名空间中运行
if [ "$(cat /proc/1/sched | head -n 1 | cut -d ' ' -f 1)" = "$(basename $0)" ]; then
    echo "Running as PID 1 in isolated namespace"
    
    # 准备systemd环境
    mkdir -p /run/systemd/system
    
    # 配置特殊的cgroup挂载
    if [ -d /sys/fs/cgroup/systemd ]; then
        mount -t cgroup -o none,name=systemd systemd /sys/fs/cgroup/systemd
    fi
    
    # 使用特殊参数启动systemd
    exec /sbin/init --distrobox-isolated-pid
else
    echo "Not running as PID 1, exiting"
    exit 1
fi
```

distrobox-enter命令增强：

```bash
        # 使用nsenter进入容器的PID命名空间

            /bin/sh -c "cd '${real_pwd}' && exec '${real_shell}' -l"
    fi
fi

# 回退到标准行为
# ... 现有代码 ...
```
