### 1. [virtio-win/kvm-guest-drivers-windows] PR #732 - 修复GPU驱动休眠后蓝屏

**基本信息**
- 🔗 **PR链接**: https://github.com/virtio-win/kvm-guest-drivers-windows/pull/732
- ⭐ **项目Stars**: 2,840
- 📅 **提交时间**: 2026-01-03
- ✅ **状态**: 已合并
- 🏷️ **标签**: `bug-fix` `bsod` `hibernate` `windows-driver` `stability`
- 📝 **改动**: +210 lines, 4 files

**问题描述**

VirtIO GPU驱动在Windows从休眠状态恢复后频繁出现蓝屏：

1. **错误表现**:
   - `DRIVER_IRQL_NOT_LESS_OR_EQUAL` (0x000000D1)
   - 错误位置: `viogpu.sys`
   - 发生时间: 系统从休眠恢复并重新初始化GPU时

2. **根本原因分析**:
   ```c
   // 在viogpudo.c文件中
   NTSTATUS VioGpuDod::HibernateRestore()
   {
       // 问题代码 - 无锁访问共享资源
       if (m_CurrentModes != NULL) {
           // 1. 显示模式信息已被清理但指针未置NULL
           // 2. 尝试访问无效内存区域
           // 3. 导致BSOD
           if (m_CurrentModes->Size > 0) {  // 访问无效内存
               InitCurrentMode();
           }
       }
       
       // 问题代码 - 资源映射错误
       if (!BuildPagingQueue()) {  // 如果在休眠前的资源没有正确释放
           return STATUS_UNSUCCESSFUL;
       }
   }
   ```

3. **复现步骤**:
   - Windows 10/11客户机在KVM/QEMU环境中
   - 使用VirtIO GPU驱动
   - 系统进入休眠
   - 唤醒系统 → BSOD

**解决方案**

全面重写休眠恢复流程，确保资源正确释放和重新初始化：

```c
// viogpudo.c - 修复后的代码

// 添加休眠状态跟踪
BOOLEAN m_IsHibernating = FALSE;
KSPIN_LOCK m_HibernateLock = NULL;

// 休眠准备
NTSTATUS VioGpuDod::PrepareForHibernate()
{
    KIRQL oldIrql;
    KeAcquireSpinLock(&m_HibernateLock, &oldIrql);
    m_IsHibernating = TRUE;
    
    // 安全释放资源
    if (m_CurrentModes != NULL) {
        // 记录当前状态以便恢复
        SaveDisplayState();
        
        // 安全释放GPU资源
        CleanupPagingQueue();
        ReleaseFrameBufferMappings();
    }
    
    KeReleaseSpinLock(&m_HibernateLock, oldIrql);
    return STATUS_SUCCESS;
}

// 休眠恢复
NTSTATUS VioGpuDod::HibernateRestore()
{
    NTSTATUS status = STATUS_SUCCESS;
    KIRQL oldIrql;
    
    DbgPrint(TRACE_LEVEL_INFORMATION, "%s: Restoring from hibernation\n", __FUNCTION__);
    
    KeAcquireSpinLock(&m_HibernateLock, &oldIrql);
    
    // 完全重新初始化GPU状态
    if (m_IsHibernating) {
        // 1. 重新初始化基本控制结构
        InitializeGpuAdapter();
        
        // 2. 重新建立命令队列
        status = BuildPagingQueue();
        if (!NT_SUCCESS(status)) {
            DbgPrint(TRACE_LEVEL_ERROR, "%s: Failed to rebuild paging queue, status: 0x%X\n", 
                     __FUNCTION__, status);
            goto Exit;
        }
        
        // 3. 恢复显示模式 (从保存的状态)
        status = RestoreDisplayState();
        if (!NT_SUCCESS(status)) {
            // 如果恢复失败，尝试设置安全默认值
            SetDefaultDisplayMode();
        }
        
        // 4. 重新扫描显示器
        RescanDisplayDevices();
        
        // 5. 发送通知给OS重新枚举显示设备
        NotifyDeviceChange();
        
        m_IsHibernating = FALSE;
    }
    
Exit:
    KeReleaseSpinLock(&m_HibernateLock, oldIrql);
    return status;
}

// 添加防止休眠期间访问GPU资源的保护
BOOLEAN VioGpuDod::IsSafeToAccessGpu()
{
    BOOLEAN isSafe = TRUE;
    KIRQL oldIrql;
    
    KeAcquireSpinLock(&m_HibernateLock, &oldIrql);
    if (m_IsHibernating) {
        isSafe = FALSE;
    }
    KeReleaseSpinLock(&m_HibernateLock, oldIrql);
    
    return isSafe;
}
```

**技术亮点**

1. **状态机设计**:
   - 使用明确的休眠状态跟踪
   - 所有GPU访问前检查状态
   - 防止休眠过程中的异步访问

2. **内存管理改进**:
   ```c
   // 避免悬垂指针和内存泄漏
   void VioGpuDod::ReleaseFrameBufferMappings()
   {
       KIRQL oldIrql;
       KeAcquireSpinLock(&m_FrameBufferLock, &oldIrql);
       
       for (UINT i = 0; i < MAX_VIEWS; i++) {
           if (m_FrameBuffers[i].Ptr != NULL) {
               // 正确取消映射
               MmUnmapIoSpace(m_FrameBuffers[i].Ptr, 
                             m_FrameBuffers[i].Size);
               
               // 重要：清除指针防止悬垂引用
               m_FrameBuffers[i].Ptr = NULL;
               m_FrameBuffers[i].Size = 0;
           }
       }
       
       KeReleaseSpinLock(&m_FrameBufferLock, oldIrql);
   }
   ```

3. **资源跟踪**:
   - 实现细粒度资源跟踪
   - 显式状态保存和恢复
   - 防止资源泄漏

4. **多级错误恢复**:
   ```c

   NTSTATUS VioGpuDod::RestoreDisplayState()
   {
       NTSTATUS status = STATUS_SUCCESS;
       
       // 尝试级别1：完全恢复
       status = RestoreCompleteState();
       if (NT_SUCCESS(status)) {
           return status;
       }
       
       // 尝试级别2：仅恢复模式，不恢复内容
       status = RestoreDisplayModeOnly();
       if (NT_SUCCESS(status)) {
           return status;
       }
       
       // 尝试级别3：回退到安全模式
       return SetSafeMode();
   }
   ```

**影响评估**

1. **用户影响**:
   - 影响所有在虚拟机中使用VirtIO GPU的Windows用户
   - 特别是频繁使用休眠的笔记本电脑用户

   - 不同显示配置 (单/多显示器，不同分辨率)
   - 100次连续休眠/唤醒循环测试

4. **技术债解决**:

   - 为高分辨率支持奠定基础

### 2. [distrobox/distrobox] PR #985 - 增强PID命名空间隔离

**基本信息**
- 🔗 **PR链接**: https://github.com/distrobox/distrobox/pull/985
- ⭐ **项目Stars**: 12,500
- 📅 **提交时间**: 2026-01-18
- ✅ **状态**: 已合并
- 🏷️ **标签**: `feature` `pid-namespace` `podman` `systemd` `isolation`
- 📝 **改动**: +180 lines, 3 files

**问题描述**

distrobox在启用systemd的容器中存在PID命名空间隔离问题：

1. **现有限制**:
   - systemd在容器中需要作为PID 1运行
   - 默认共享宿主机的PID命名空间
   - 导致容器内进程可以看到宿主机进程

2. **用户需求**:
   - 增强容器隔离性
   - 支持在容器内运行需要完整PID命名空间的应用
   - 保持systemd功能的同时提高安全性

3. **技术冲突**:
   ```bash
   # 现有命令 - 功能不完整
   distrobox create --name test-box \
     --image fedora:37 \
     --init --additional-flags "--pid=host"
   
   # 问题：--init (systemd) 与 PID隔离存在冲突
   # systemd需要作为PID 1运行，但隔离的PID命名空间也需要自己的PID 1
   ```

**解决方案**

实现新的PID命名空间管理策略，兼容systemd需求：

```bash
#!/bin/bash
# distrobox-create - 增强版PID命名空间隔离

# 新增配置选项
DBX_PID_ISOLATION="default"  # 可选: default, isolated, host
DBX_INIT_APPROACH="auto"     # 可选: auto, systemd, none

# 主逻辑增强
generate_container_command() {
    # ... 现有代码 ...
    
    # 根据配置选择适当的PID命名空间策略
    case "${DBX_PID_ISOLATION}" in
        "isolated")
            if [ "${DBX_INIT_APPROACH}" = "systemd" ]; then
                # 特殊情况：需要systemd + PID隔离
                # 使用podman/docker的特殊参数组合
                container_command+=(--pid=private)
                container_command+=(--init-path=/usr/bin/distrobox-init-proxy)
            else
                # 标准PID隔离
                container_command+=(--pid=private)
            fi
            ;;
            
        "host")
            # 使用宿主机PID命名空间
            container_command+=(--pid=host)
            ;;
            
        "default"|*)
            # 默认行为取决于容器引擎和init方式
            if [ "${DBX_INIT_APPROACH}" = "systemd" ]; then
                # systemd默认需要使用宿主机PID
                container_command+=(--pid=host)
            fi
            ;;
    esac
    
    # ... 现有代码 ...
}
```

实现init代理来处理PID命名空间冲突：

```bash
#!/bin/bash
# /usr/bin/distrobox-init-proxy

# 此脚本作为容器内PID 1运行
# 目的：协调隔离的PID命名空间和systemd需求

# 检测我们是否在隔离的PID命名空间中运行
if [ "$(cat /proc/1/sched | head -n 1 | cut -d ' ' -f 1)" = "$(basename $0)" ]; then
    echo "Running as PID 1 in isolated namespace"
    
    # 准备systemd环境
    mkdir -p /run/systemd/system
    
    # 配置特殊的cgroup挂载
    if [ -d /sys/fs/cgroup/systemd ]; then
        mount -t cgroup -o none,name=systemd systemd /sys/fs/cgroup/systemd
    fi
    
    # 使用特殊参数启动systemd
    exec /sbin/init --distrobox-isolated-pid
else
    echo "Not running as PID 1, exiting"
    exit 1
fi
```

distrobox-enter命令增强：

   ```bash
       if [ "${engine_name}" = "podman" ]; then
           # Podman 3.0+支持更好的PID隔离
           if version_greater_equal "${engine_version}" "3.0"; then
               echo "isolated"
               return 0
           fi
       elif [ "${engine_name}" = "docker" ]; then
           # Docker需要特殊处理
           if version_greater_equal "${engine_version}" "20.10"; then
               echo "isolated"
               return 0
           fi
       fi
       
       # 默认回退到host模式
       echo "host"
       return 0
   }
   ```
